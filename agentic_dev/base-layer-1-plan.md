## 3. Engine constraint — `multiply` blend (resolved)

MapLibre GL JS does not support CSS-style blend modes on raster layers. Of the three paths originally considered, **path 2 (pre-baked multiply) was executed**:

- The tile-level multiply variant was chosen over the GDAL-on-source-rasters approach, because the existing per-tile PNG pyramids already share the same XYZ grid by construction — no alignment/reproject step needed. `base-layer-1-prep/scripts/multiply_tiles.py` walks both pyramids in parallel and emits `out_rgb = relief_rgb × hillshade_luma / 255` per pixel, preserving relief alpha. Hillshade transparency is forced to luma=255 so we never see black artifacts at coverage edges. ~4 min wall-clock for the 15,719 tiles.
- Spot-check at z=12 tile (2399,1190): relief `(112,168,143)` × hillshade luma `249/255 ≈ 0.976` → output `(109,164,139)`. Math correct, cartography correct.

**One pyramid, exact blend, no engine workaround at runtime.** Compositions #2 and #3 can reuse `relief_hillshade` directly (composition #3's "relief multiply, opacity 40%" becomes `raster-opacity: 0.4` on the same source).

If a future composition needs hillshade *independently* of relief (e.g. variable per-section opacity on hillshade alone), we can ship the standalone hillshade pyramid in a follow-up — the original §4.1 instructions below are kept for reference.

### 5.3 Wire it into `MainMap.tsx`

Base #1 is the **default** basemap; the per-section selector lands as a no-op for now (returns 1 for every section) and gets the lookup table from `Описание лонгрида - порядок слоев.csv` later in Phase 5 PR B. This keeps this PR mergeable without depending on PR B.

Four insertion points:

1. **`useBaseComposition(activeItemId)` hook (new).** Today: returns `BASE_COMPOSITIONS[1]` unconditionally. Later: reads `SECTION_TO_BASE_ID: Record<string, 1|2|3|...>` (also baked from the CSV in Phase 5 PR B) and selects the right composition. Doing the hook now means PR B is a single-file change.
2. **Map style spec (`MainMap.tsx:426-441`).** Replace the inline `sources: { relief: {...} }` + `layers: [{ id: 'relief', ... }]` with a single `relief_hillshade` raster source. Keep the style spec raster-only and call a new `addBaseComposition(map, BASE_COMPOSITIONS[1])` on `map.on('load')` to layer the four vectors on top.
3. **New function `addBaseComposition(map, comp)`** — for each `VectorEntry`, fetch the GeoJSON URL from `fileUrlByName`, reproject (reuse `transformCoordinates`), `addSource` and `addLayer` with paint built from `VECTOR_STYLES[entry.style]`. For each `RasterEntry`, `addSource` + `addLayer`. Idempotent — early-return on existing source IDs so a base swap can call it repeatedly.
4. **Refactor `ensureLayerOnMap`** (`MainMap.tsx:303-378`) to consult `VECTOR_STYLES[styleName]` first, fall back to today's `mask_` two-palette logic when the style is unknown. Section-overlay layers must `addLayer(..., beforeId)` with `beforeId` set to a sentinel layer id `__overlay_anchor__` (a transparent fill layer added at the top of `addBaseComposition`) so base composition stays underneath.

This split also matters for caching: since the base layers are global, we add them once per map instance and never re-create them on section change. Only when the hook later returns a *different* composition (chapter 2 → base #3) does `addBaseComposition` run again, and it should `removeLayer`/`removeSource` the previous composition's layers first. Ship without the swap path for now; add it when composition #3 lands.
